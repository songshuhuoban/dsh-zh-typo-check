## 一、DSH 侧：机制先说清楚

DSH 的插件市场叫 **Discover**，它不托管任何插件，只读**用户自己配置的 index URL**；
而且**默认一个源都不配**。索引格式 1 就是一份 JSON，列出可安装的 bundle 及其展示元数据
（来源：`@deepseek-ai/dsh-plugin-market` 与 `dsh-plugin-market-index` 包文档）。

所以「上架 DSH 市场」在技术上等于：**让某个被广泛配置的索引收录你**。
目前生态里被广泛配置的索引只有一个——`awesome-dsh-plugin` 那一份。

## 二、主市场：awesome-dsh-plugin

- 仓库：<https://github.com/awesome-dsh-plugin/awesome-dsh-plugin>
- 站点：<https://awesome-dsh-plugin.com>
- 下游：`dsh-market` 插件、`dshmarket` 插件都实时读它的 `plugins.json`

### 提交方式

在 `data/plugins/` 下**新增一个文件**，文件名 `owner__repo.yml`：

```yaml
url: https://github.com/songshuhuoban/dsh-zh-typo-check
name: songshuhuoban/dsh-zh-typo-check
category: ui
description:
  en: 'Inline Chinese typo and half-width punctuation check in the DSH composer: instant rule layer plus an optional local model (ONNX, 103 MB) for semantic typos — no API key, no token cost, nothing leaves the machine.'
  zh: '在 DSH 输入框里直接标出中文错别字和半角标点：规则层即时响应，可选再装一个本地模型（ONNX，103 MB）补语义错——不需要 API key，不消耗 token，文字不出本机。'
icon: https://raw.githubusercontent.com/songshuhuoban/dsh-zh-typo-check/main/assets/icon-180.png
```

### 硬性要求（逐条对照我们的现状）

| 要求 | 我们 |
| --- | --- |
| 仓库公开、有真实可用代码 | ✅ |
| 根 `package.json` 声明 `dsh.bundle`（或 `packages/` 等子包） | ❌ **阻塞** |
| 仓库创建满 1 天（CI 自动查） | ⏳ 今晚达标 |
| 加 `dsh-plugin` topic | ❌ 待加 |
| 描述只讲功能、不夸大，且会被对着代码核 | 待写 |
| `description.en` 必填（中文可留空由维护者补） | 待写 |
| 一个 PR 最多 3 条 | 我们 1 条，没问题 |
| `icon` 必须是 GitHub 托管的**位图**（png/jpg/webp），SVG 被拒 | ❌ 目前只有 `icon.svg` |
| `screenshots.json` 可选但强烈建议（详情页 App Store 式截图） | ❌ 待做 |

### 分类

可选值：`agi` `ui` `usage` `theme` `model` `identity` `session` `memory` `tools`
`wsl` `browser` `vision` `voice` `docs` `skill` `workflow` `git` `notify` `dev`
`security` `remote` `market` `fun`

我们属于 **`ui`**（输入框内的界面增强）。选偏了维护者会直接改，不会打回。

### 评审会看什么

CI 只验形式（清单、仓库年龄、格式、README 能否重新生成），**合并前维护者会读代码**，
核对描述里的每一句声明。夸大是唯一会让好插件被打回的理由。

### npm 包

已发布的话，市场的下载量映射**自动**从 registry 采集（包内 `repository` 必须指回被收录的仓库）。
条目里**不要**手写 `npm:` 字段，会被校验拒绝。我们已经满足。

## 四、阻塞项怎么解（结构决策）

主市场的 CI 读的是**仓库根**（或 `packages/` / `plugins/` / `apps/` 子包）的 `package.json`。
我们现在把发布包放在 `bundle/`，这个目录名不在允许列表里。

两条路：

### 方案 A：改成 monorepo 子包（改动小）

把 `bundle/` 改名为 `packages/zh-typo-check/`，条目写成：

```yaml
url: https://github.com/songshuhuoban/dsh-zh-typo-check/tree/main/packages/zh-typo-check
name: songshuhuoban/dsh-zh-typo-check#zh-typo-check
```

文件名相应变成 `songshuhuoban__dsh-zh-typo-check--packages-zh-typo-check.yml`。
安装走带 `path:` 参数的 git URL。

- 优点：改动集中在路径，`npm publish` 仍从子目录发
- 缺点：多一层目录，安装命令对用户稍微长一点

### 方案 B：仓库根就是插件包（改动大，但最符合生态惯例）

把 `bundle/*` 挪到仓库根，根 `package.json` 变成插件清单
（`dsh.bundle` + `files` 白名单 + `dependencies`），开发用的 `src/` `tools/` `data/` 留在旁边。

这条路正是社区里所有插件的样子，`dsh plugin add github:owner/repo` 直接可用，
npm 发布也从根目录（`files` 白名单保证包内只有运行时文件）。

- 优点：和其它插件完全同构，用户与维护者都不用理解我们的特殊结构
- 需验证：之前试过平铺但当时 `main` 指向 `bundle/index.js` 且 pnpm 软链是旧的，
  失败原因没能排除干净。要重做一遍并实测 `install_bundle` + 客户端加载

**建议先做方案 B**（与生态同构，长期收益最大）；如果验证受阻，退回方案 A。

## 五、竞品与定位

同赛道已有插件：**honlnk/dsh-input-assist**

- 收录于 2026-09-20，30 天下载 1,533，分类 `ui`
- 能力：输入补全（ghost text，走 DeepSeek FIM）+ 错别字检查（浏览器本地词典 228 条 + LLM 上下文校对）
- 依赖 `DEEPSEEK_API_KEY`，LLM 层消耗 token

我们的差异点，写描述时必须体现：

| 维度 | dsh-input-assist | 我们 |
| --- | --- | --- |
| 检查方式 | 词典（228 条） + LLM 调用 | 规则（13 万词表） + **本地 ONNX 模型** |
| API key | 需要 | **不需要** |
| token 成本 | 有 | **零** |
| 隐私 | 文本发给 LLM | **不出本机** |
| 离线 | LLM 层不可用 | **全离线可用** |
| 响应 | 200ms（词典）/ 800ms（LLM） | 规则即时 / 模型约 225ms |
| 额外能力 | 输入补全 | 整句通畅度（实验） |

一句话定位：**不联网、不花钱、不看你的字**的中文检查。

评测里「100% 精确率、零误报」这个数据也可以写进长文，但要如实说明语料规模（75 句）。

## 八、相邻生态（T4，需移植）

这些不是「提交同一个包」，而是把**检查核心**（`core.mjs` + `l1.mjs` + `checker.mjs` + `infer.mjs`）
移植到别的宿主里。核心已经和 DSH 解耦，移植成本主要在 UI 层。

| 平台 | 需求 | 难度 | 备注 |
| --- | --- | --- | --- |
| VS Code Marketplace | Markdown/注释里的中文校对 | 中 | 已有「中文文案校对」类插件，卷，但流量最大 |
| Obsidian 社区插件 | 笔记里的中文校对 | 中 | 中文笔记用户对错别字敏感，插件市场审核相对简单 |
| Chrome / Edge 扩展 | 任意网页输入框 | 中高 | 想象空间大，但要处理各站点 DOM |
| 飞书 / 钉钉 | 聊天与文档 | 高 | 最初灵感来源，但开放平台门槛高 |

**先做 VS Code 还是 Obsidian**：Obsidian 更容易（插件生态小、审核快、用户对中文校对有明确需求），
VS Code 流量更大但竞争更激烈。

## 十、风险与注意

1. **描述会被核对代码**：不要写「支持 13 万词表」却不说明那是词表规模而非规则条数。
2. **收录不等于安全审查**：多个目录都明确声明这一点，我们要在 README 里自己说清楚
   插件做了什么（读输入框、下载 103 MB 模型、监听 mousemove），别等人来问。
3. **同类竞争按「谁更好」判定**：awesome-dsh-plugin 明说先收录只是平局时的排序，
   后来者更好就能进。所以我们和 dsh-input-assist 并存是正常的，关键是把差异写清楚。
4. **模型下载是安装门槛**：103 MB + 需要允许 `onnxruntime-node` 构建脚本。
   README 里已经写了，但市场详情页的截图里最好也体现「不装模型也能用」。
5. **别做刷星**：雷达按 star 排序，多个目录都取 GitHub 星数；但夸大和刷量会直接影响评审。
